# 進め方の用語

案件の進め方で使う言葉の一覧。**案件を知らない人が、承認カードやボードを読むときに引く**ためのもの。製品そのものの用語（画面やデータの名前）は、各案件の用語集に置く。

カードや報告の本文では、ここの言葉は初めて出るところで言い換える（段＝wave のように）。

---

## 仕事の組み立て

| 言葉 | 意味 | 例 |
|---|---|---|
| 段（wave） | 順番に進める大きな区切り。前の段が終わってから次の段の作業を始める（機能のまとまりが着手可＝承認済みなら、前の段が終わっていなくても始められる） | 「6 入居者の登録」「13 本番環境の構築」 |
| 機能のまとまり（feature） | 段の中の、機能ごとのまとまり。**着手の承認はこの単位** | 「探す（4 画面のモック）」 |
| 作業（task） | 機能のまとまり（feature）の中の仕事の 1 項目。変更（PR）は機能のまとまりごとに 1 本 | 「絞り込みの画面を作る」 |
| 設計メモ | 作る前に考えをまとめた文書。承認されると作業に分けられる | `docs/draft/<名前>.md` |
| 常設の段 | 終わりの無い仕事を置く段 | 「ハーネスの改善」 |
| 段の終わりの条件 | その段が終わったと言える条件。段の本文に「出る条件」として書く。満たすと次の段の作業を始められる（承認済みの機能のまとまりは、満たす前でも始められる） | 「出る条件のコマンド: exit 0（日付・commit）」 |
| 止める依存（blocked by） | 「これが終わるまで、あれは始められない」というつながり | 「#12 は #10 に止められている」 |
| 着手順 | 同じ段の中で、作業をどの順に始めるかの数字（小さいほど先） | 1, 2, 3 |

## 状態（8 つ）

| 状態 | 意味 | 動かす人 |
|---|---|---|
| 承認待ち | 始めてよいか、人の承認を待っている | 入ったときは自動 |
| 着手可 | 承認された。始めてよい | 人（機能のまとまり）／AI（その中の作業） |
| 判断待ち | どれにするか、人の判断を待っている（判断カードがあるもの） | AI |
| 依存待ち | 先の作業が終わるのを待っている（承認待ちの機能のまとまりの作業は、先の段が終わるまで待つ） | AI |
| 進行中 | AI が作業している | AI |
| レビュー中 | 変更（PR）ができて、確認と取り込みを待っている | 自動 |
| 完了 | 変更が取り込まれて終わった | 自動（残りは見回りの AI） |
| 保留 | **今はやらないと決めた**もの。理由と再開の条件を本文に書く | AI |

- **「保留」は「待っている」ではない。** 外部の手続きや判断を待っているものは、判断待ちか人の作業にする。保留を待ちに使うと、本当に止めたものと区別がつかなくなる。
- **「完了」は作業が終わったこと。** 製品の中の「相談の完了」などとは別の意味。

## 題名の目印

| 目印 | 意味 | どう進むか |
|---|---|---|
| `[User]` | 人が手を動かす作業（外部への申込・契約・実機での確認） | 人の作業カードを見て、人が行う |
| `[操作]` | 人の資格や権限が要るが、AI が行う操作（本番の設定・管理画面での変更） | 承認カードで承認を取ってから、AI が行う（`hirai-task start --approved`） |
| `[Decision]`（案件による） | 判断を求める問いの題名に付ける目印。道具は特別扱いしない | 状態は「判断待ち」、本文に判断カード |

## 頼み方

| 言葉 | 意味 |
|---|---|
| 承認カード | 「始めてよいか」を頼むときの 7 行の型。1 行目に決めることと推奨。戻せるかを必ず書く |
| 判断カード | 「どれにするか」を頼むときの型。期限・目的・選択肢（得るもの・失うもの）・推奨 |
| 人の作業カード | 人の手が要る作業を頼むときの型。やること・誰が・手順・終わったら |
| 承認ビュー | ボードの中の、承認待ちの機能のまとまりだけを並べた画面。**着手の承認はここで受ける**。承認しないなら「保留」にして理由をコメント、直してほしいならコメント |
| 推奨 | AI が勧める答え。根拠と、頼っている推測をカードに書く |
| 推測 | 確かめていないこと。カードでは必ず「推測」と書く |

型の本体は `docs/rules-reference/approval-template.md`。

## 変更と取り込み

| 言葉 | 意味 |
|---|---|
| PR（変更の提案） | 作業の結果をまとめた変更。確認して取り込む |
| 取り込み（merge） | PR を本線に入れること。**出来上がりの確認であって、着手の承認ではない**（設計メモの承認を設計の PR の merge で受けることはある。着手の承認とは別） |
| 着手できる | 承認され、止める依存が無い作業。`hirai-task ready` が出す（機能のまとまりが着手可なら、前の段が終わっていなくてもよい） |

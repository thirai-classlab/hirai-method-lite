# コンテキスト予算と出力の形

`rules/_meta.md` の予算制 (T0 合計 3,000 tokens) と層構造の、数値的な裏付け。あわせて「エージェントの発話の形」について user から繰り返し出た要求の記録。

---

## 1. コンテキストの肥大は、ツール呼び出しの失敗として現れる

**何が起きたか**: セッション開始時点のコンテキストが 11 層で約 **146K トークン**に達していた時期、ツール呼び出しの解析失敗が頻発した。構造を組み直して約 **100.1K (-45.9K、-31.4%)** まで減らした。目標は -44% だったが、届かないまま**受け入れた** (理由は項目 4)。2026-05-28 → 2026-06-01 観測。

**なぜ重要か**: コンテキスト予算は「もったいない」という感覚の問題ではなく、**動作の信頼性に直結する**。ツール呼び出しの構造化出力が壊れる現象 ([`subagent-operations.md`](subagent-operations.md) 項目 2) と同じ場所で起きている。

**出典**: 旧ハーネス `docs/tasks/list.md` task-51 (2026-05-28〜06-01)。

---

## 2. 選べる手の数そのものがコストになる

**何が起きたか**: コンテキスト肥大の原因を追ったところ、**選択可能なエージェント 144 種 / スキル 63 種**の存在自体が主因の 1 つだった。エージェントやスキルは、使わなくても**説明文が常に載っている**。使用頻度 × 責務の重複 × プロジェクト固有性で選別し、エージェントを 144 → 76 に減らした (68 種 + スキル 11 種を退避)。2026-06-02 観測。

**どう対処するか**: 「あっても困らない」は誤り。**あるだけで毎ターン課金される**。退避先と復帰手順を用意したうえで、使っていないものを外す。

新ハーネスが意図的に小さいのは、この観測が理由の 1 つである。

**出典**: 旧ハーネス `docs/tasks/list.md` task-72 (2026-06-02)。

---

## 3. 毎ターン繰り返す注意書きは、効果を失いながらコストだけ残す

**何が起きたか**: 毎ターン注入される注意書きが「注意の希釈」を起こしていた。無条件の毎ターン注入を **4 種 → 0 種**に削減。別の整理でセッション開始時の出力を 3257B → 623B (**-81%**)、毎ターンの助言コストを **-186 トークン/ターン**にした。

さらに、「ツール呼び出しのたびに目的を宣言する」という規則は 2026-06-01 に「**ターン冒頭 1 回**」へ緩和された。理由は削減だけでなく、散文とツール呼び出しの往復が増えることで**ツール呼び出しの構造が壊れるリスクが上がる**ため (項目 1 / [`subagent-operations.md`](subagent-operations.md) 項目 2 と同根)。

**どう対処するか**: 言うのはセッション開始かターン冒頭に 1 回。毎ターンの繰り返しは効果を買わず、信頼性を落とす。

**出典**: 旧ハーネス `docs/tasks/list.md` task-21 / task-73、`.claude/rules/why-x5-output.md` v11 (2026-06-01)。

---

## 4. サイズ目標のために内容を削らない

規範文書の圧縮タスクで、2 ファイルが目標を大きく下回ったまま**成功と判定された**記録がある。判断の基準は「フォーマット維持 + 内容の無損失」であり、バイト数ではなかった。詳細は [`design-process.md`](design-process.md) の項目 7 を参照。

**この移植作業にも同じ基準が適用される。**

---

## 5. 出力の形について、user が実際に求めたこと

旧ハーネスには、エージェントの発話の形をめぐる user の指摘が繰り返し記録されている。形式そのものは旧ハーネス固有だが、**要求の中身は移植可能**。

### 5-1. 前置きの儀式は 1 行で足りる

「何のために何をやるか」を宣言する形式は、**10 版にわたって改訂され、そのすべてが user に却下された**。記録に残る却下の言葉:

| 版 | 内容 | user の反応 |
|---|---|---|
| v1 | 6 段階の固定フォーマット | 「固定するな」 |
| v2 | 必須 3 項目 | 「それも固定するな」 |
| v3 | 全項目オプション | 「現在の作業と代替案は必須」 |
| v4 | 1 文にまとめる | 「いや、多段で」 |
| v5 | 矢印付きの多段 | 「認知負荷が高い」 |
| v7 | セクション記号つき | 「§ は不要」 |
| v8 | 順序を反転 | 「上が目的、下が今の作業」 |
| v9 | 4 セクション | 「冗長、不要」 |
| v10 | **1 行**: `<何のため> のため、<何をやる> を行う` | 確定 |

**教訓**: 儀式的な前置きは、構造を足すほど嫌われる。**目的と作業を含む 1 行**が着地点だった。検討した代替案は頭の中で踏み、出力には書かない。

この経緯を知らずにゼロから形式を再発明すると、同じ 10 回を繰り返すことになる。

**出典**: 旧ハーネス `.claude/rules-details/why-x5-output/v1-v10-history.md` (〜2026-05-23)。

### 5-2. 4 件以上の一覧はテーブルにする

2026-05-23 の直接指摘 — 進捗やタスクの一覧を箇条書きで出すと視認性が悪い。**4 件以上、または列が複数あるもの**はマークダウンのテーブルにする。3 件以下や文中の列挙はそのままでよい。

**出典**: 旧ハーネス memory `feedback_chat_list_output_as_table` (2026-05-23)。

### 5-3. 自動で進める設定のとき、確認で終わらない

自動モードにもかかわらず AI が確認を求めて止まる事象が繰り返し観測された。user がセッションログを貼って指摘した実例がある。

記録されている**確認質問の言い回し**: 「進めてよいですか」「OK ですか」「お待ちします」「次の指示お待ちしています」「どちらにしますか」「どうしますか」。

ただし `rules/core.md` のとおり、**確認を省いてよいのは戦術的な判断だけ**である。新しい設計の追加 / 決めた内容の変更 / 元に戻せない操作は、自動モードでも承認を取る。旧ハーネスでは、この境界を誤って「一切聞くな」と一般化した結果、**設計書が承認を経ずに書かれる**違反が実際に起きている (2026-05-23)。

**出典**: 旧ハーネス `.claude/rules-details/modes/five-layer-enforcement.md` (2026-05-26) / `.claude/CommonRules.md` Critical Operational Lessons (2026-05-23)。

### 5-4. 些末なコマンドに儀式を付けない

設定を 1 行書き換えるだけのコマンド (モード切替など) に、目的の宣言や代替案の検討を付けるのは過剰である、と 2026-05-12 に user から明示された。結果は 1〜2 行だけ返す。

**出典**: 旧ハーネス memory `feedback_skip_why_x5_for_mode_command` (2026-05-12)。

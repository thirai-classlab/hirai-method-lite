# 設計・承認・規範づくりの落とし穴

`rules/core.md` の「設計の起点」「事実で答える」、`rules/tasks.md` の draft 承認フローの背景。

---

## 1. 設計が前提にする外部依存は、起案時に存在を確認する

**何が起きたか**: ある API の設計が、設定ファイルに 6 つのキーが存在することを前提にしていた。実装フェーズで担当が調べたところ**そのキーは 1 つも存在しなかった**。設計どおりに作れば、その機能は恒久的に「未保存」を返し続ける — つまり動かないものが出来上がるところだった。2026-05-29 観測。

**なぜ起きたか**: 設計レビューは「値が一致するかの判定ロジック」だけを見て、**参照先のキーが実在するか**を一度も確認しなかった。前提が暗黙だったため、レビューの対象にすらならなかった。

**どう対処するか**:

- draft の詳細設計に「**依存の実在確認**」の欄を作り、起案の時点で `grep <key> <file>` を実行して結果を脚注に書く
- レビュアーのプロンプトに「参照している外部リソースが実在するか確認せよ」を入れる
- 実装を委譲するときは「前提にしている依存を先に grep で確認し、食い違ったら実装前に報告せよ」と書く

**出典**: 旧ハーネス memory `feedback_design_external_dependency_verification` (2026-05-29)。

## 2. パスを推測したまま実装しない

**何が起きたか**: 設計書がメモリファイルの保存先を `~/.claude/projects/<hash>/memory/` と推測して書いていた。実際は別の場所だった。そのまま実装していれば、**一度も発火しない仕掛け**が出来上がっていた。2026-05-12 観測。

**なぜ起きたか**: 設計書は物理的な実在 (パス / ファイル配置 / ハッシュの計算方法) についての仮定を含むが、実装前にそれを検証する手順が無かった。

**どう対処するか**: 実装着手前に Glob / Read で実パスを確認する。設計と実態が食い違ったら**設計書のほうも直す**。推測のパスを subagent に渡すのは同じ罪 — subagent はその推測どおりに実装する。

**出典**: 旧ハーネス memory `feedback_verify_path_before_implementation` (2026-05-12)。

## 3. 前提が崩れたときは止まらず、案と推奨を出す

**何が起きたか**: 項目 1 の前提崩壊に直面したとき、メインエージェントは停止せず、1 通のメッセージで「壊れた前提 + 案 A (最小修正) / 案 B (全面再設計) / 案 C (機能縮小)、それぞれの工数と得失、AI の推奨は C」を提示した。user が即答して案 C が採用され、4 領域の並列簡素化で **417 行を削除、手戻りゼロ**で完了した。2026-05-29。

**なぜ**: 前提の崩壊は仕様・スコープに影響するので **user の判断点**であって、作業を止める障害ではない。黙って戦術的に回避すると user の意図から乖離する。

**どう対処するか**: 崩壊を検知したら 1 通で「何が壊れたか + 2〜3 案 (各: 工数・利点・欠点) + AI の推奨 1 つ」を出す。即答が返れば推奨案で継続する。user が不在なら状態を保存して止まる。

**出典**: 旧ハーネス memory `feedback_design_precondition_collapse_user_choice` (2026-05-29)。

## 4. 承認済み設計への「縮小方向の変更」は再承認を要しない

**何が起きたか**: 実装の途中で user から「この項目は保存しなくてよい」という仕様変更が入った。承認済みの設計書だったが、破棄して再承認を取り直せば大きな手戻りになる。

**どう対処するか**: 承認を維持したまま、設計書の承認履歴に 1 行追記する — 仕様変更の内容 / 影響 / 「元の承認の延長であり再承認不要」。

**適用できるのは縮小方向だけ**: 機能の削除・簡素化・ケースの削減は延長として扱える。**スコープの拡張・新機能の追加・アーキテクチャの変更は再承認が要る**。

**出典**: 旧ハーネス memory `feedback_user_spec_change_within_approved_draft` (2026-05-29)。

## 5. 設定値は「定義 + 読む側 + テスト」の 3 点セットで出す

**何が起きたか**: あるタスクが設定値のスキーマだけを追加し、「それを読んで動作を変える処理は次フェーズで」と先送りした。次フェーズは来なかった。数か月後、別のタスクで規範文書に直書きされた数値のほうが使われ、**設定値は誰にも読まれないまま**だった。user から「設定が効いていない」と報告されて発覚。2026-05-30。

**なぜ起きたか**: 定義があって消費者がいない設定値は死んだ設定である。さらに、規範文書に数値を直書きしたことが「設定値を無視してよい」ことを正当化してしまった。

**どう対処するか**:

- 設定値は同じタスクの中で 3 つ揃える — **(1) 定義 (2) それを読んで動作を変える処理 (3) 値を変えると挙動が変わることを示すテスト**
- 規範文書に数値を直書きしない。「キー X に従う」と書き、確認コマンドを併記する
- 「次フェーズで強制する」という先送りは、必ず追跡タスクにする。追跡しない先送りは実現しない

**出典**: 旧ハーネス memory `feedback_config_value_needs_consumer_and_smoke` (2026-05-30)。

## 6. 規範を作ったら、同じセッションで既存の 1 件に適用する

**何が起きたか**: 規範を策定するタスクの最終フェーズで、**進行中の既存タスク 1 件をその新しい規範に沿って作り直した**。その場で「最終ステップは 2 段ではなく 3 段必要だ」という規範の不備が判明し、リリース前に修正できた。2026-05-23。

**なぜ**: dogfooding を後のセッションに回すと、規範の欠陥 (前提の誤り / 抽象度の誤り / 既存との衝突) が、書いた本人の文脈が新しいうちに見つからない。

**どう対処するか**: 規範を作るタスクには「既存 1 件に適用する」フェーズを含め、そこで見つかった欠陥をフェーズ内で反映してから確定する。

**出典**: 旧ハーネス memory `feedback_norm_then_dogfood_pattern` (2026-05-23)。

## 7. 内容の劣化はサイズ目標より重い

**何が起きたか**: 規範文書を圧縮するタスクで、2 つのファイルがサイズ目標を大きく下回った (目標 -5K に対して実績 -1.3K / -0.3K)。それでも成功と判定した。

**なぜ**: 規範文書の第一の目的は**エージェントの振る舞いの正本を保つこと**であり、サイズ削減は副次的な目標にすぎない。条文が密なファイルには捨てるものが無いので、そこで無理にサイズを削れば条文そのものを消すことになる — それは退化である。

**どう対処するか**: サイズ目標は努力目標として書き、完了条件には「フォーマット 100% 維持 / 内容の無損失」を置く。**内容の欠落は CRITICAL、サイズ未達は情報レベル**として扱う。

**出典**: 旧ハーネス memory `feedback_ssot_priority_over_size_target` (2026-05-28)。

## 8. 規範文書の常時ロードは、物理配置で制御するしかない

新ハーネスの T0 / T1 / T2 という層構造と、**T2 を `.claude/rules/` の外に置くという判断**の直接の由来。

**何が起きたか**: 2026-05-28、旧ハーネスのセッション開始時のコンテキストが約 146K トークンあり、そのうち規範ファイル 7 本で約 50K を占めていた。そこで規範を「要約層 (常時) + 詳細層 (必要時)」に分割し、詳細層のファイルに `paths: []` (空配列) を書けばロードされないと考えた。

**実際にはロードされた**。空配列を書いた 6 ファイルはすべてセッション開始時のコンテキストに入っていた。物理的に `.claude/rules/` の外へ移動して初めて解決した。

**2026-08-21 の訂正**: 上記から「`paths:` は効かない」と一般化したが、これは誤りだった。実際のコンテキストを直接観測したところ、**実在するグロブパターンを書いたファイルはロードされておらず**、ロードされていたのは frontmatter を持たないファイルだけだった。公式ドキュメントの記述とも一致する。

**正しい理解**:

| 書き方 | 挙動 |
|---|---|
| 実在するグロブ (`paths: ["src/**"]`) | 該当ファイルを触るまでロードを遅延する。**条件ロード機構として正しく効く** |
| 空配列 (`paths: []`) | 仕様に定義がなく、常時ロードにフォールバックする |
| frontmatter 無し | 常時ロード |

つまり `paths:` は**条件ロードの機構であって、除外の機構ではない**。「ロードさせない」ことを保証する手段は、`.claude/rules/` の外に物理的に置くことだけである。

**新ハーネスへの反映**: T2 (`docs/rules-reference/`) を `rules/` の外に置いているのはこの結論による。`paths:` の書き忘れが即座に常時ロードへの昇格を意味する以上、**書き忘れうる仕組みではなく、書き忘れても壊れない配置**を選んだ。

**裏側のコスト — 条件ロードにすると、その規範は存在しないのと同じになる**: 別の事案 (2026-05-23) では、タスク運用の規範に `paths: ["docs/tasks/**", "docs/draft/**"]` を付けたところ、それらのパスを読んだターンでしか規範が文脈に入らなくなった。結果として「設計 → 承認 → タスク化」のフローがモデルの認識から落ち、**設計書が承認を経ずに直接書かれる**違反が実際に発生した。対処は frontmatter を外して常時ロードに戻すこと。

つまり `paths:` は**両刃**である。常に成り立つべき規範を条件ロードにすると守られなくなり、作業限定の規範を常時ロードにすると予算を食う。**「常に成り立つべきか」を先に判定してから層を決める** — これが `_meta.md` 条 2 (既定は T1、T0 にするには立証が要る) の裏付けになっている。

**もう 1 つの教訓 (メタ)**: 最初の記録は「`paths:` は効かない」という**過度の一般化**だった。1 つの反例 (空配列) から機構全体を否定していた。訂正できたのは、実際のコンテキストを再観測し、公式ドキュメントに当たり直したからである。**記録された教訓それ自体が誤っている可能性を、定期的に疑う。**

**出典**: 旧ハーネス memory `feedback_layer_a_b_two_tier_rule_structure` (2026-05-28) / `feedback_paths_frontmatter_does_not_exclude` (2026-05-28 記録 → 2026-08-21 訂正)。

## 9. 計測値に基づいて設計する前に、計測そのものを検証する

**旧ハーネス最大級の空振り**。数値が 5600 倍ずれていた。

**何が起きたか**: ある設計書が「観測ログの 56% (7048 件中 3916 件) が解析に失敗している」= 「学習データの半分が捨てられている」という前提で書かれ、重大な課題として扱われていた。実データを測り直した結果、**28583 件中 11 件 = 0.04%** だった。

56% という数字は**カスケード障害の副産物**だった。1 件の制御文字が混入したせいで、それ以降のすべての行の解析が連鎖的に失敗していた。さらに悪いことに、健全性を測る監査コマンドの指標自体が同じカスケードに汚染されていたため、**計測器が誤った読みを追認していた**。

結果として、その前提で計画されていたフェーズは「**存在しない問題への解決策**」と判定され、丸ごと不要になった。2026-05-23 観測。

**どう対処するか**:

- 計測値を設計の前提に置くときは、**その計測方法自体を先に検証する**。特に集計値がカスケード的な処理を通っている場合 (1 件の失敗が後続に波及する形) は、per-record の実測と突き合わせる
- 根本原因の修正と**計測器の修正を別の作業として扱う**。計測器を直さないと、直したことも確認できない
- 前提が消えたら、その前提の上に積んだ計画も**取り消す**。作りかけを惜しんで続行しない
- 誤りが判明した元の設計書には、脚注で「この数値は誤計測だった」と残す。消さない

**出典**: 旧ハーネス `docs/tasks/list.md` task-27 / task-32 (2026-05-23)。

## 10. 着手前に「すでに直っていないか」を履歴で確認する

**何が起きたか**: 指摘事項に対する作業を計画・委譲したが、その指摘は既存の commit ですでに解消済みだった。空振りのエージェント起動が発生した。2026-05-21 観測。

**どう対処するか**: 計画段階で `git log --all --grep <キーワード>` を掛け、該当する修正が入っていないか確認する。

**出典**: 旧ハーネス `.claude/rules-details/workflow/14-stage.md` (2026-05-21)。

## 11. 規範文書に、無い保証を書かない

**新ハーネスにとって最も重要な設計上の制約**。旧ハーネスの記録を移植するにあたり、この項目が全体の書き方を規定する。

**何が起きたか**: 旧ハーネスでは、ドキュメントと規範が「この操作は BLOCK される」と説明している一方で、実際の設定ではその機構が無効になっている、という状態が生じた。記録された帰結は次のとおり。

> モデルにはドキュメントを必須と読ませるが、実際の境界では止まらない。結果として **AI が存在しない制約に基づいて萎縮し、行動を避ける**。

これを是正するために複数のタスクが費やされた。

**なぜ起きたか**: 正本が 2 つあった — 規範の散文と、実際の設定。両者が食い違うことを禁じる仕組みが無かった。

**新ハーネスでの意味**: 新ハーネスには機械強制の仕組みがほとんど無い。したがって**規範は強制の言葉で書いてはならない**。「hook が止める」「BLOCK される」と書けば、旧ハーネスが多大なコストを払って直したのと同じ失敗を、初日から再現することになる。

実際に止まるのは `settings.json` の `permissions` に登録された操作だけであり、それ以外は**すべて指針である**。指針は指針として書く。

**出典**: 旧ハーネス `.claude/CommonRules.md` §Design Constraints、および `docs/tasks/list.md` task-70 / task-88 / task-103。

## 12. ある時点で観測した挙動を、恒久的な教義に固定しない

**何が起きたか**: 2026-05-23、「リポジトリ外への書き込みは全経路で拒否される」と確信度 0.85 で結論づけ、「常に user に手動実行を依頼する」という規範を作った。**2026-05-26 に同じ操作が 4 リポジトリすべてで成功**し、確信度 0.92 で覆った。3 日で失効した規範である。

**なぜ起きたか**: ある時点のサンドボックスの挙動を、仕様として一般化した。

**どう対処するか**: 判断順序を「まず試す → 実際に拒否されたら迂回する」に変える。「以前ダメだったから」を根拠に試さないのをやめる。**規範に失効条件を書く**のはこのためでもある。

**出典**: 旧ハーネス `.claude/rules-details/development-process/cross-repo-write.md` (2026-05-23 → 2026-05-26 で supersede)。

## 13. 初期状態は「きれいに見える」ようにする

**何が起きたか (ノイズ側)**: インストール直後の診断コマンドが 8 件の問題を報告した。大半は使っていない機能に関する無害な警告だったが、**AI はそれを実在する問題として扱い**、対処を試み始めた。

**何が起きたか (逆の側)**: 空のタスク台帳がテンプレートで完全に埋まっていたため、**「空」ではなく「完了済み」に見え**、計画を始める動機が働かなかった。

**なぜ**: エージェントは初期状態を「正常な基準線」として読む。基準線がノイズだらけなら幽霊を追いかけ、基準線が完成して見えるなら何もしない。

**どう対処するか**: 既定の構成は警告 0 件で立ち上がるようにし、追加機能はオプトインにする。空の台帳には「ここに最初のタスクを追加する」と読める見出しを置く。

**出典**: 旧ハーネス `docs/tasks/list.md` task-87 / task-90 / task-91。

## 14. 欠陥を 1 件直したら、同じクラスを横断検索する

詳細は [`plugin-development.md`](plugin-development.md) の項目 7 を参照。要点: バグ報告のスコープは「見つかった場所」であって「存在する場所」ではない。1 箇所直して閉じてよいのは、欠陥のクラスをキーワード化して全体を grep し、他に該当が無いと確認したときだけ。

同種の記録として、旧ハーネスにはブランチ名の正規表現が 3 箇所に重複しており、「変更時は 3 箇所同時に更新する義務」が明文化されていた。**この義務には裏付けとなる事故の記録が無い (未確認)** ため、予防的に書かれたものと見られる。定数や正規表現が N 箇所に散る構造そのものを避けるほうが確実である。

**出典**: 旧ハーネス `.claude/rules/git-workflow.md` §変更時の同期義務。

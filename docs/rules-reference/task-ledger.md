# タスク台帳と構造の実務

**この文書は、やることをファイルの一覧表（`docs/tasks/list.md`。台帳）に持つ形のリポの記録である。** GitHub Project に載せる形のリポの規範は `rules/tasks.md`、立ち上げは [`project-setup.md`](project-setup.md) を読む。どちらの形かは `rules/tasks.md` の冒頭で見分ける。

## 2 つの形の区別（項目 1 の「中間階層を作らない」を読み違えないために）

| | 台帳の形 | GitHub の形 |
|---|---|---|
| 仕事の組み | 1 task = ゴール 1 文 + N step の 2 段。task の上に段を足さない | wave → feature → task の 3 段（項目「種別」と sub-issue） |
| 完了の判定 | task 1 行 | task は PR 1 本で閉じる。feature と wave は sub-issue の帯（子の完了数）で見る |
| 状態 | 未着手 / 進行中 / 完了 の 3 種 | Status 8 値 |

項目 1 が禁じたのは、**1 つの task の中に**フェーズ・ステップを重ねて完了判定ができなくなったこと。GitHub の形の wave と feature は task の**上**に置く別の issue で、完了は task 単位で閉じる。3 段に分けること自体は事故の再発ではない。

`rules/tasks.md` の「1 task = ゴール 1 文 + N step」「status は 3 種」「完了条件は検証可能に」の背景（台帳の形）。台帳の形が **5 列 / status 3 種 / task の中に中間階層なし**という素朴な形をしているのは、旧ハーネスがそれぞれ逆方向に振れて失敗した記録があるためである。項目 2（完了条件）と項目 5（書き込みはメイン専任）は、どちらの形にも通じる。

---

## 1. 中間階層を作るとタスクの完了判定ができなくなる

**何が起きたか**: 1 つのタスクが **5 フェーズ × 14 ステップ**まで膨れた。具体的な支障は 3 つ。

1. 「フェーズ 1 完了」の時点で、**タスク自体が終わったのかどうか誰も答えられない**
2. ステップ単位の状態が台帳に出ない (台帳の行はタスク単位だったため)
3. 概要欄に、タスクの目的とステップの作業内容が混在した

2026-05-23 → 2026-05-25 観測。

**どう対処するか**: 階層を 2 段に潰す。**1 タスク = 1 ゴール + N ステップ**。フェーズ / ウェーブ / サブフェーズといった中間階層を作らない。ステップの状態は台帳の行として見えるようにする。

概要の書き分けも決めておく — **タスクの概要は「何のため × 何をやる × 何ができるようになる」、ステップの概要は作業内容だけ**。

**出典**: 旧ハーネス `.claude/CommonRules.md` Critical Operational Lessons / `.claude/rules-details/task-management/six-articles.md` (2026-05-23 → 2026-05-25)。

## 2. 完了条件は再現可能なコマンドで書く

旧ハーネスが NG 例として明記していたもの:

| NG | なぜダメか |
|---|---|
| 「テストが通る」 | どのテストか、どう実行するかが無い |
| 「動作する」 | 観察者によって判定が変わる |
| 「検証済み」 | 何を検証したのか復元できない |

OK の形は「`bash tests/x-smoke.sh` が exit 0」「`GET /health` が 200 を返す」のように、**別の人 (別のセッションの AI) が同じ手順で再実行できる**もの。

`rules/core.md` の「事実で答える」— コマンドと exit code を併記せよ — と同じ要求である。

**出典**: 旧ハーネス `.claude/rules-details/task-management/six-articles.md`。

## 3. N 件をまとめて計画したら、その場で N 行を台帳に置く

**何が起きたか**: 26 件のタスクからなるロードマップが承認され、設計書が次々に書かれていった。しかし**台帳はその間ずっと空のままだった**。user が進捗を明示的に尋ねて初めて発覚した。2026-05-25 観測。

**なぜ起きたか**: user 自身による事後分析で 4 層の原因が特定されている。

1. タスク作成の手順が「1 件ずつ」を前提にしていた
2. その手順がタスク構造の規範と矛盾していた
3. 「計画中」を表す状態に 2 つの意味 (設計起案中 / 一括計画で先置き) があり、区別できなかった
4. AI が「今は一括計画モードだ」と認識できなかった (単純な操作ミス)

**どう対処するか**: 一括計画 (3 件以上) のときは、ロードマップ承認の**直後に N 行を台帳に置く**。中身は後から埋める。台帳が空なら「計画が無い」と読まれるので、計画があることを先に台帳で表明する。

新ハーネスの status は 未着手 / 進行中 / 完了 の 3 種で、旧ハーネスのような二義的な「計画中」状態を持たない。**一括計画の N 行は 未着手 として置けばよい** — 上記の原因 3 は構造的に消えている。

**出典**: 旧ハーネス `.claude/CommonRules.md` Critical Operational Lessons / `.claude/rules-details/task-management/plan-first.md` (2026-05-25)。

## 4. 完了 commit に台帳の更新を含める

**何が起きたか**: タスク完了の commit が台帳の状態更新を含んでいなかった。PR が merge された後、台帳の行は「進行中」のままだった。統合先ブランチ上での直接編集は禁じられていたため、**台帳の 1 行を直すためだけに追加の PR** が必要になった。2026-05-29 観測。

**なぜ起きたか**: 台帳の状態は、その PR に同乗させないと後から直せない。merge 後に気づいても遅い。

**どう対処するか**: 完了 commit の `git add` に、実装ファイルと**台帳を必ず含める**。委譲するなら、プロンプトの `git add` 対象リストに台帳のパスを明記する。

`rules/tasks.md` の「完了 commit に台帳を含める」はこの事故が出典である。

**出典**: 旧ハーネス memory `feedback_task_completion_commit_must_include_list_md` (2026-05-29)。

## 5. 台帳の更新をサブエージェントに任せない

複数の subagent が共有の一覧表を編集すると、古い内容を読んだ書き込みが他者の更新を巻き戻す。実測と対処は [`subagent-operations.md`](subagent-operations.md) の項目 4 を参照。

`rules/tasks.md` の「台帳更新はメイン専任」「サブエージェントは台帳を読むだけ」はこれが出典である。

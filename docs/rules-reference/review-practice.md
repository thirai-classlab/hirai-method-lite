# レビュー運用の実務

`rules/code.md` の「レビュー fan-out」の背景。**回数を機械強制しない代わりに、何をもって収束と見なすか**の判断材料をここに置く。

---

## 1. 「全員 approve」は収束の証明にならない

**何が起きたか (事例 1)**: 4 人の reviewer (test-automator / pr-test-analyzer / tdd-guide / qa-expert) が揃って「CRITICAL + HIGH = 0」を確信度 0.91〜0.94 で報告し、クローズを推奨した。同じ巡で `code-reviewer` だけが確信度 0.62 で以下を発見した。

- 設定を 2 回書き換えると値が破損する CRITICAL (1 回目の書き込みの断片が 2 回目の値に混入)
- エスケープ文字の往復変換が壊れる HIGH
- 環境によって読み出し結果が変わる非対称性の HIGH

いずれも一時ファイルに**実際に再現ケースを作って**発見したもの。2026-05-27 観測。

**何が起きたか (事例 2)**: 5 人が何も見つけなかった巡で、`code-reviewer` だけが実際の古い bash (3.2) 上で 2 件の CRITICAL を発見した。関数内の変数代入がコマンド置換の出力に混入し、147 行中 73 行がゴミになって TUI が起動時点で死んでいた。再現結果が他の reviewer と食い違ったときは、`git show <hash>:<path>` で当時のコードを取り出して同じ環境で測り直し、矛盾を解消した。

**なぜ起きたか**: 多くの reviewer は静的レビューと「書いてすぐ読む」程度のテストで止まる。**再書き込み / 往復変換 / 環境差 / 特定ビルド固有の挙動**は、能動的に再現を作らないと出てこない。

**どう対処するか**:

- コスト削減で reviewer を絞るときも、**`code-reviewer` は最後の巡まで残す**
- `code-reviewer` のプロンプトに「再書き込み・往復変換・環境差の能動再現を行え」と明示する
- 2 人の再現結果が矛盾したら、指摘を退けずに**当時のコードを取り出して同一環境で測り直す**

**出典**: 旧ハーネス memory `feedback_code_reviewer_deep_test_advantage` (2026-05-27)。

## 2. 修正が次の巡で新しい CRITICAL を生む

**何が起きたか**: 2 巡目の修正で 1 巡目の CRITICAL 7 件をすべて閉じたにもかかわらず、3 巡目で**別軸の新規 CRITICAL が 4 件**出た。

| 新規 CRITICAL | 軸 |
|---|---|
| 2 巡目が追加した設定ファイルのコメントが、パーサの仕様と矛盾し、無効化したはずのフラグが有効と評価された | 規範矛盾 |
| 新しいフラグが既知キー一覧に登録されず、環境変数の上書きスナップショットから漏れた | 構造の後方互換 |
| 1 巡目のキャッシュ修正が、別経路に 74 回の逐次プロセス起動 (約 370 秒のブロック) を残した | 性能問題の移動 |
| 2 段階書き込みの中断経路が空の履歴を書き、ロールバックが「0 件復元・成功」を無言で返した | サイレントなデータ損失 |

さらにタイムスタンプの精度不足によるファイル上書き (データ損失) が確信度 0.96 で追加され、収束には 5 巡を要した。2026-05-29 観測。

**なぜ起きたか**: 修正は既存の機構と結合するので、**新しい失敗軸を作る**。規範との矛盾、後方互換の破壊、性能問題の転移、サイレントな失敗が典型。「1 巡目の指摘が全部閉じた」は「壊れていない」ではない。

**どう対処するか**:

- 反復は 3〜5 巡が現実的な収束域。1 巡で終わる前提を置かない
- N+1 巡目の reviewer プロンプトには、**「N 巡目の修正が正しいか」と「N 巡目の修正が作った新しい軸を探せ」の両方**を書く

**出典**: 旧ハーネス memory `feedback_iter_fix_introduces_new_crit_pattern` (2026-05-29)。

## 3. 実機で確認していない CRITICAL は、軽い検証で先に潰す

**何が起きたか**: reviewer が確信度 0.78 で「変数の二重宣言により構文エラーになる、起動時点で死んでいる可能性」という CRITICAL を報告し、**自分で「実機では確認していない」と注記していた**。構文チェックを 1 コマンド走らせる検証用 subagent を立てたところ、exit 0。grep のヒットは別の変数名への部分一致による偽陽性で、指摘は確信度 0.99 で棄却された。

この誤報に従っていれば、ファイル 1 本の全面書き直しで 30 分以上を失っていた。2026-05-29 観測。

**なぜ起きたか**: reviewer は静的読解から報告する。grep の部分一致と未検証の仮説は、もっともらしい CRITICAL を生む。**確信度 0.85 未満 + 「未検証」の自己注記**が、その署名になっている。

**どう対処するか**: CRITICAL が以下のいずれかに当てはまるとき、決定論的な検証 (構文チェック / 型チェック / ビルド / lint / 起動確認) を走らせる軽量 subagent を即座に立てる。

- 決定論的な検証コマンドを経由していない
- reviewer 自身が推測であると注記している
- 確信度が 0.85 未満

検証 subagent は読み取りと実行だけに絞り (編集させない)、実行コマンド・exit code・grep 結果・判定・確信度を返させる。他の reviewer がまだ走っている間に並行して立ててよい (ただし同時 2 件の上限内で)。

**出典**: 旧ハーネス memory `feedback_main_agent_must_verify_syntax_after_subagent` (2026-05-29)。

## 4. 複数観点の指摘は重複するのが正常 — 重複排除して領域地図にする

**何が起きたか**: 6 人の reviewer を並列起動した 1 巡目で、重複排除後 **39 件のユニークな指摘** (CRITICAL 7 / HIGH 12 / MEDIUM 13 / LOW 7) が出た。分布に意味がある。

| 指摘 | 発見者数 |
|---|---|
| 書き込みの原子性 | 4 人 |
| パス traversal | 2 人 |
| アクセシビリティ | 1 人 (UI 担当のみ) |

**なぜ重要か**: ある観点の盲点は別の観点が拾う。**1 人しか挙げていない指摘こそ、その観点を入れた理由**である。多数決で落とさない。

**どう対処するか**: 重複は 1 行にまとめ、指摘者を併記し、重大度は最も高いものを採る。そのうえで**領域 (サーバ / UI / テスト / 設定) でラベル付け**すると、そのまま修正の分担表になる。実際、上記の 39 件は 4 領域に分けた 4 件の修正 subagent に落とし込まれ、競合ゼロ・設計乖離ゼロで完了した。

**出典**: 旧ハーネス memory `feedback_iter_unique_aggregation_and_parallel_fix_pattern` (2026-05-29)。

## 5. reviewer は固定リストではなく対象から選ぶ

**なぜ**: 固定の登録表は、不要な reviewer を動員する (コスト) か、領域固有の reviewer を落とす (レビュー不足) かのどちらかになる。適切な顔ぶれは UI / DB / API / 言語 / セキュリティの含有量で変わる。

**どう選ぶか**: テスト観点の基礎 (`tdd-guide` / `test-automator` / `qa-expert` / `pr-test-analyzer`) に、対象領域の reviewer を足す。UI なら `ui-designer` / `accessibility-tester` / `e2e-runner`、スキーマなら `database-reviewer`、API なら `api-designer`、言語別 reviewer、認証や入力を触るなら `security-reviewer`。

**人数の下限を数値で決めない**: 旧ハーネスは「5 人以上」という数値を規範に直書きし、その結果**設定ファイル側の上限値が無視される**事故を起こした (2026-05-30)。数を規範に埋め込むと、数を満たすこと自体が目的化する。

**出典**: 旧ハーネス memory `feedback_dynamic_reviewer_selection_pattern` (2026-05-23) / `feedback_config_value_needs_consumer_and_smoke` (2026-05-30)。

## 6. 「代替案で approve」は設計からの乖離を隠す

**何が起きたか**: 設計書が定めた 2 段階のナビゲーションが、1 巡目で「設計からの逸脱」として CRITICAL 指摘された。2〜3 巡目で「区切り行付きのフラットな一覧」という妥協案として approve され、6 人の approve を得て merge された。**user の手元確認で「2 段階メニューになっていない」ことが判明**し、追加タスクが必要になった。2026-05-27 → 2026-05-29。

**なぜ起きたか**: レビューの判定が approve / reject の二値で、「妥協案が設計からどれだけ離れたか」がどこにも記録されなかった。妥協が積み上がっても誰も気づかない。

**どう対処するか**:

- クローズ時に、**設計書の中核要件 (関数名 / 状態名 / API 名) を実装に対して grep して確認する**
- 端末やブラウザでしか確認できない機能は、完了条件に「user が手元で §X の挙動を確認する」を入れる
- 妥協案を approve したときは、設計書に「§X から乖離、代替案でクローズ、追跡先: <slug>」を記録し、**その場で追跡タスクを起こす**

**出典**: 旧ハーネス memory `feedback_iter_approve_design_drift_user_verify` (2026-05-27/29)。

## 7. UI は「動く」と「見た目が正しい」が別の軸

**何が起きたか**: 2026-05-27 に user から直接の指示があった —「UI 実装後はビジュアルの検証を必須化してください。ブラウザ検証は agent-browser skill を利用する。スクリーンショットなども利用する。e2e とは別」。

**なぜ**: HTTP レスポンス / ファイル内容 / プロセス状態は自動テストで検証できるが、**レイアウト・スタイルの適用・状態の可視化・オフライン時の劣化表示**は検証できない。型チェックとテストの通過は代替にならない。

**どう分けるか**:

| 検証対象 | 手段 |
|---|---|
| HTTP / ファイル / プロセス状態 | 自動テスト |
| ピクセル / CSS / DOM の状態 | ブラウザ + スクリーンショット |
| ネットワーク遮断時の挙動、システム設定 (ダークモード等) への追随 | ブラウザ必須 |

撮る対象は、主要ブレークポイント (例: 320 / 768 / 1024 / 1440)、主要な状態 (初期 / 選択中 / 入力中 / エラー / 成功通知)、両テーマ。ターミナル UI は対象外。

**出典**: 旧ハーネス memory `feedback_ui_visual_verification_mandate` (2026-05-27) / `feedback_step6_visual_verification_browser_skill_template` (2026-05-29)。

## 8. reviewer に「対象だけ」を渡すと、他タスクとの衝突が全部抜ける

**何が起きたか**: 6 人の reviewer を並列で 1 つの設計書に当てたが、**誰一人として**「他タスクとの重複」「既存規範との矛盾」「既存実装を再利用できる余地」を検出しなかった。user から直接、レビュアーのプロンプトを直すよう指示が入った。2026-05-28 観測。

**なぜ起きたか**: プロンプトが reviewer の視野を「対象成果物のみ」に限定していた。中を見る目しか与えなければ、外との関係は見えない。

**どう対処するか**: レビュアーのプロンプトに、対象・観点・報告形式・確信度に加えて **5 つ目の項目「プロジェクト整合性」** を入れる。

> タスク台帳・依存タスク・既存の規範・README を読んだうえで、(a) 他タスクとの重複 (b) 前提の破壊 (c) 規範との矛盾 (d) 既存実装の再利用余地 を報告せよ。

旧ハーネスは、この項目に対して「台帳: 関連なし」とだけ答えて**実際には台帳を読んでいない**回答を NG 例として明記している。読んだ根拠 (行番号・引用) を求めるとよい。

**出典**: 旧ハーネス `.claude/rules-details/workflow/reviewer-prompt.md` §起源 (2026-05-28)。

## 9. 全面書き換えの後は、実装者の自己確認では足りない

詳細は [`subagent-operations.md`](subagent-operations.md) の項目 7 を参照。要点だけ:

- 実装者は「新しいものが動くか」しか見ないので、**旧仕様を前提にしたテストが壊れたことに気づけない**。全面書き換えの後は main か reviewer がフルのテストを実際に走らせる
- 古くなったテストは削除せず、**理由を書いて SKIP にするか、新しい仕様に向け直す**
- 構造チェックのガードは、コードの書き方が変わると**無言でマッチ 0 件になる**。実値でマッチすることを確認する

**出典**: 旧ハーネス memory `feedback_ui_rewrite_stale_smoke_regression` (2026-06-03)。

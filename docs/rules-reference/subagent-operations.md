# サブエージェント運用の実務

並列実行・委譲・共有ファイル競合の実測記録。数値はすべて実際の観測値で、推定は「未確認」と明記する。

`rules/core.md` の「同時起動は 2 件まで」「重い作業は委譲する」の背景がここにある。

---

## 1. 同時起動数の上限は 2 — 4 件以上で成果物ゼロになる

これは本領域で最も重要かつ最も新しい知見であり、**それ以前の「6 並列は安全」「独立タスクなら 3〜4」という記録を上書きする**。

### 観測 1: 4 件同時起動で全滅 (2026-08-27、本セッション)

独立したファイル領域を担当する 4 件の subagent を 1 ターンで同時起動した結果:

| 件数 | 結果 |
|---|---|
| 3 件 | 600 秒間無進捗のまま停止 |
| 1 件 | API 接続が切断 |
| 成果物 | `git init` と空ディレクトリ 2 つのみ。ファイル 0 件 |

同じ作業をそのまま **2 件ずつ** (1 件完了通知を受けてから次を起動) に落として再実行したところ、**5 件連続で成功**、各 3〜10 分で完了した。

### 観測 2: 9 reviewer 並列で workflow が stall (2026-07-06、旧ハーネス)

3 chain × 3 レビュー観点 = 9 reviewer を並列起動した workflow で、**30 agents / 22 分 / subagent トークン 4.4M** を消費して停止した。実装フェーズは完走してファイルも着地したが、Review ブランチが 1 本も戻らず、後続の Verify / Fix / Commit が走らなかった。

### 何が原因か

失敗は **同時実行数そのもの**に相関する。特定のオーケストレーションツールの問題ではない (観測 1 はツールを使わない素の並列起動で起きている)。閾値は 4 件以上。上流の負荷特性が原因と推測されるが、**根拠は取れていない (未確認)**。

### どう運用するか

- **既定は同時 2 件**。次の 1 件は完了通知を受けてから起動する
- reviewer を多数立てたいときは (a) 観点を統合して 3 本にする (b) chain ごとに逐次にする (c) 広く 1 巡 → 絞って 1 巡の 2 ラウンドにする
- 1 つのフェーズが **20 分以上無進捗**なら殺して残りを組み直す

**出典**: 本セッション実測 (2026-08-27) / 旧ハーネス memory `feedback_workflow_9_reviewer_parallel_stall_risk` (2026-07-06, 2026-08-21)。旧ハーネスの `feedback_six_parallel_subagent_batch_safe` (6 並列成功、2026-05-28) と `feedback_parallel_subagent_context_endurance` (最大同時 2、9 件累計、2026-05-23) は、より新しい上記の観測に置き換わっている。

## 2. 1 ターンに複雑な tool 呼び出しを詰め込むと、呼び出しそのものが壊れる

**何が起きたか**: 散文 + 4〜6 件の長大な tool 呼び出し (10 行以上、引用符やマークアップ片を含むプロンプト) を 1 ターンに並べたところ、呼び出しのラッパータグが脱落し、**何も実行されずに本文として表示された**。同じ内容を再送しても同じように壊れるため、外からは無限ループに見える。2026-06-01 に観測、user から「動いてない / バグっていませんか?」と繰り返し指摘された。

単一の Bash 呼び出しでも、コマンドが十分複雑 (`;` `|` の多用、grep の選択、多数の引用符、日本語混在) なら同じことが起きる。

**なぜ起きたか**: 同時呼び出し数 × ペイロードの複雑さ (長さ・引用符・マークアップ) が閾値を超えると構造化出力が壊れる。

**どう対処するか**:

- 手書きの tool 呼び出しは **1 ターン 1〜2 件**まで
- 長いプロンプトは**ファイルに書いて subagent に読ませる**
- 検証は行内の複合 grep ではなく、**スクリプト 1 本**にまとめて 1 呼び出しにする
- 壊れたと気づいたら**同じバッチを再送しない**。1 件ずつに落とす

**推測として棄却された説**: 「tool の前に `call` と書くとプレフィックスが剥がれる」という説は誤り。`call` は壊れたラッパーの残骸であって原因ではない。

**出典**: 旧ハーネス memory `feedback_multi_tool_block_serialization_failure` (2026-06-01)。

## 3. 独立作業は並列が既定、逐次は本当の依存があるときだけ

**何が起きたか**: 2026-06-02 の長時間セッションで約 30 件の subagent をほぼ 1 件ずつ逐次起動し、user から「可能な限り並行で作業を適切なサブエージェントに降って」と明示指示を受けた。

**どう対処するか**: 逐次にしてよいのは 3 つだけ — (a) 段階依存がある (b) 同一ファイルへの書き込みが重なる (c) commit 順序を守る必要がある。それ以外は並列。ただし同時 2 件の上限 (項目 1) が優先する。

**出典**: 旧ハーネス memory `feedback_parallel_subagent_delegation_default` (2026-06-02)。

## 4. 共有ファイルは単一書き手にする (barrier パターン)

**何が起きたか (競合の側)**: 5 件の並列 subagent が、それぞれ担当分の行を共有の README 一覧表に書き込んだ。1 件が古い内容を読んだまま書き戻したため、**main が既に commit 済みだった他タスクの行が巻き戻った**。main が `git status` の diff で気づいて手動復元。2026-06-01 観測。

**何が起きたか (成功の側)**: 3 chain を並列で走らせた際、共有ファイル群 (config yml / メタデータ TSV / 共通ライブラリ / smoke 登録表) の変更を **1 件の barrier subagent に集約**したところ、競合ゼロで完走した。2026-07-06 観測。

**なぜ起きたか**: 共有ファイルは収束点であり、並列書き手は互いを見ずに read-modify-write する。最後の書き手が勝ち、途中の更新が消える。ファイル丸ごとの置換を伴う配置手順では部分マージも起きない。

**どう対処するか**:

- 起動前に**ファイル領域の割当表**を作り、重複をゼロにする
- 共有ファイル (台帳 / 一覧表 / 設定 / 共通ライブラリ / テスト登録) は **main 専任か barrier subagent 1 件**に集約する
- subagent のプロンプトに「**共有 index を編集するな**」と明記する。「main が index に使う」と書くだけでは足りない — subagent は親切心で編集してしまう
- subagent には成果物の一覧を完了報告で返させ、main が集約する
- 並列バッチの後は、共有ファイルの `git diff` を見て巻き戻った行が無いか確認する

**出典**: 旧ハーネス memory `feedback_subagent_shared_index_edit_race` (2026-06-01) / `learning_yml_metadata_barrier_single_subagent` (2026-07-06)。

## 5. ファイル間の契約は事前に 1 箇所で決めて全プロンプトに貼る

**何が起きたか**: `app.js` (描画関数が `getElementById('main-panel')` を呼ぶ) と `index.html` (`id="view-container"` を出力し `main-panel` は無い) を別々の並列 subagent が実装した。描画関数は早期 return し、**UI 全体が一切描画されない**まま、両ステップとも「完了」として commit された。静的 smoke は各ファイルを個別に grep していただけなので緑のまま通った。ブラウザでの目視検証で初めて発覚。2026-05-29 観測。

**なぜ起きたか**: 相互参照するファイル間の契約 (DOM id、シンボル名、API のフィールド名、イベント名) は各 subagent からは見えない。ファイル単位の静的 grep は「存在」を確認するだけで「一致」を見ない。

**どう対処するか**:

- 起動前に main が**共有契約を 1 箇所に書き**、同じ値を全 subagent のプロンプトに貼る
- ファイル間の整合は、静的なクロスチェック (`app.js` の全 `getElementById('X')` に対応する `id="X"` が `index.html` にあるか) か、実際の描画確認で検証する
- **UI において「smoke 全部緑」を完了の根拠にしない**

**出典**: 旧ハーネス memory `feedback_parallel_subagent_cross_file_contract_drift` (2026-05-29)。

## 6. 並列 subagent に git を触らせるときの禁止事項

**何が起きたか**: 2026-05-12、同一ブランチで並列 commit させていた subagent の 1 件が `git reset --soft HEAD^` を実行し、**他のエージェントの commit を巻き込んで orphan 化**させた。

**なぜ起きたか**: 並列 subagent は互いの index / HEAD を観測しない。各自が「今ステージされているのは自分の変更だけ」と信じて commit し、`git reset --soft HEAD^` は間に入った他者の commit を越えて HEAD を戻す。

**どう対処するか**: 並列 subagent のプロンプトに以下を必ず書く。

1. `git add <対象ファイルを明示>` のみ。`git add .` / `-A` / `-p` は禁止
2. **`git reset` は全形式禁止**
3. 誤ってステージしたら `git restore --staged <file>` で戻し、復旧できなければ報告して止まる

完全に分離したいときは worktree 隔離を使う。orphan 化してしまった commit は `git log --all --reflog --oneline` で探して `git cherry-pick <sha>` で拾える。

**より簡単な代替**: commit は main 専任にし、subagent には**ファイルを書かせるだけ**にする。これで本項の問題は消える。

**出典**: 旧ハーネス memory `feedback_parallel_subagent_git_conflict` (2026-05-12)。

## 7. サブエージェントの自己申告は main が実物で検証する

**何が起きたか**: subagent が「ファイルを配置した、smoke 21/21 通過、確信度 0.92」と報告した。main が実物を確認したところ、**配置そのものが失敗しており、subagent は古いファイルに対してテストしていた**。フォールバック経路が偶然期待どおりの挙動を出したため、自己検証は通ってしまった。損失は 30〜45 分。2026-05-29 観測。

別の事例では、UI を全面書き換えた subagent が自分のブラウザ確認で「エラー 0」と報告したが、**フルの smoke を回すと 6 件 FAIL** していた。旧 UI を前提にしたテストが壊れたことは、実装者自身のブラウザ確認では見えない。さらに悪いことに、構造チェック用のガード自体が新しい記法にマッチせず**無言で何も検査しない状態**になっていた。2026-06-03 観測。

**なぜ起きたか**: 「テストが緑 + 高い確信度」は「書き込みが着地した」ことの証明にならない。実装者の自己検証は、自分が作ったものが動くかしか見ない。

**どう対処するか**:

- subagent がファイル配置を報告したら、main が `Read` / `git status` / `git diff` で**実物を確認する**
- subagent 側にも「配置後に `grep -n <key> <file>` して期待件数を確認し、合わなければ再試行せよ」と書く
- 全面書き換えの後は main か reviewer が**フルのテストスイートを実際に走らせる**。grep で済ませない
- 構造チェックのガードは、**実値でマッチすることを確認する**。マッチ 0 件でも通ってしまうガードは存在しないのと同じ

**注記**: 配置失敗の直接原因は旧ハーネス固有 (サンドボックスの書き込み制限を回避するための一時ディレクトリ経由の配置手順) だが、**「委譲先の自己申告を実物で検証する」という原則は仕組みに依存しない**。

**出典**: 旧ハーネス memory `feedback_subagent_staging_mv_silent_fail` (2026-05-29) / `feedback_ui_rewrite_stale_smoke_regression` (2026-06-03)。

## 8. 停止した並列バッチは git の状態から回収できる

**何が起きたか**: レビュー段で停止した workflow でも、完走済みの実装フェーズが書いたファイルは**すべて working tree に残っていた**。2026-07-06 観測。

**なぜ起きたか**: 各フェーズの出力は完了時点で working tree に着地し、後続フェーズの成否とは独立している。

**どう対処するか**: 停止を検知したら、まず `git status --porcelain` / `git diff --stat --cached` / `git log --oneline -5` を控える。次に (a) 期待ファイルの実在を Read で確認 (b) 一時ファイルの残骸を削除 (c) スクリプトの構文チェック (d) 個別テスト (e) 全体テスト、を回してから、**未完了のフェーズだけ**組み直す。全部やり直さない。

**出典**: 旧ハーネス memory `feedback_workflow_partial_failure_recovery_via_git_state` (2026-07-06)。

## 9. 委譲先の選び方 — 専門エージェントがあるのに汎用を使わない

**何が起きたか**: 9 種以上の専門エージェントが用意されていたにもかかわらず、テスト拡充を汎用エージェントに委譲し、テスト専門の知見を失った。同じセッションでリファクタリングも汎用に委譲し、振る舞いを保つための知識を失った。2026-05-25 観測。

**どう対処するか**: タスクのキーワードに対応する専門エージェントを既定にし、該当が無いときだけ汎用を使う。テスト → `test-automator` / `tdd-guide`、リファクタリング → `refactoring-specialist`、レビュー → 言語別 reviewer、といった対応。

**出典**: 旧ハーネス `.claude/rules-details/development-process/parallelization-origin.md` (2026-05-25)。

## 10. 独立した作業をまとめて 1 件に委譲すると、そのぶん遅くなる

**何が起きたか**: ファイル領域が重ならない 3 つの独立した作業を 1 件の subagent にまとめて委譲し、**実時間で約 3 倍**かかった。2026-05-25 観測。

**どう対処するか**: 独立した作業が 2 件以上あれば並列が既定 (同時 2 件の上限内)。まとめる場合は理由 (競合 / 共有ファイル / 順序依存) を明示する。

**出典**: 旧ハーネス `.claude/rules-details/development-process/parallelization-origin.md` (2026-05-25)。

## 11. 委譲したら待たない — メインは別の作業を進める

**何が起きたか**: 背景で subagent を起動した後、メインエージェントが完了通知を受動的に待つだけの状態でターンを閉じた。user から「なぜ自動で実行を続けないのか?」と**複数回**指摘された。2026-05-12 観測。

**なぜ起きたか**: 「完了通知待ち」を正当な停止状態として扱ってしまった。

**どう対処するか**: subagent 実行中、メインは以下のいずれかを優先順に進める。

1. 別の独立したタスクに着手する
2. メインしかできない作業 (台帳の同期、タスクファイルの作成、設計 draft の起案)
3. 規範や記録の整備

止まってよいのは、残りのタスクがすべて依存待ちか、すでに全件委譲済みのときだけ。

**出典**: 旧ハーネス `.claude/CommonRules.md` Critical Operational Lessons (2026-05-12)。

## 12. 複数エージェントが追記するファイルはロックが要る — 逐次テストでは検出できない

**何が起きたか**: 並列の subagent が共有のログファイルに追記した結果、ファイルが破損した。別の事例では、台帳の行を更新する処理が**並列実行で 10 回中 10 回失敗**した。いずれも逐次実行のテストは通っていた。2026-05-25 / 2026-05-28 観測。

**どう対処するか**: 複数の書き手を持つファイルには atomic なロックを掛ける。移植性のある基本手段は `mkdir` (存在すれば失敗する atomic 操作)。そして**テストを実際に N 並列で走らせる**。修正後は 144 並列の追記で破損ゼロを確認している。

**教訓の一般形**: 並行性のバグは逐次テストで検出できない。並行性を主張するなら並行でテストする。

**出典**: 旧ハーネス `docs/tasks/list.md` task-34 / task-53 (2026-05-25 / 2026-05-28)。

## 13. サブエージェントの書き込み権限は、メインと同じとは限らない

**何が起きたか**: subagent から `.claude/` 配下への書き込みが、`Write` / `Edit` / Bash のリダイレクトの**3 経路すべてで拒否**された。前景・背景・worktree 隔離のいずれでも同じ。メインからの書き込みは通る。2026-05-13 観測。

**注意 (別の事例)**: 同じように「リポジトリ外への書き込みは全経路で拒否される」と結論づけた記録が 2026-05-23 にあるが、**2026-05-26 に同じ操作が成功して覆っている**。

**どう対処するか**:

- 委譲先が書けない場所があるなら、**プロンプトに配置手順を明示する** (どこに書き、どう移すか)
- ただし「ある時点で観測した拒否」を恒久的な仕様として固定しない。まず試し、実際に拒否されたときだけ迂回する
- **権限による拒否は作業を止める理由にしない**。委譲するか、経路を変える

**出典**: 旧ハーネス `.claude/rules-details/development-process/staging-strategy.md` (2026-05-13) / `.../cross-repo-write.md` (2026-05-23 の結論を 2026-05-26 が上書き)。

## 14. プロンプトに書くべき定型 4 項目

上記の事故から逆算した、並列委譲時のプロンプト必須項目。

| 項目 | 書くこと |
|---|---|
| 担当ファイル | 触ってよいパスを列挙し、それ以外は禁止と明記する (特に共有 index) |
| 共有契約 | 他のファイルと共有する id / シンボル / API フィールド名を、決定済みの値として貼る |
| git 制約 | `git add <明示>` のみ / `git reset` 禁止 / commit するか否か |
| 報告形式 | 成果物一覧 + 検証に使ったコマンドと exit code + 確信度 (`confidence: 0.X`) |

確信度を出させるのは、低い値 (0.85 未満) と「実機で確認していない」という自己注記が、検証を要する報告を見分ける信号になるため。過去の実績では、確信度の中央値 0.91〜0.95 が完走したバッチの水準だった。

**出典**: 旧ハーネス memory 複数 (`feedback_six_parallel_subagent_batch_safe` / `feedback_parallel_subagent_context_endurance` / `feedback_main_agent_must_verify_syntax_after_subagent`)。

# テストの実務

`rules/code.md` の「テスト先行」「テストは実挙動を検証する」の背景と、テスト自体が壊れる / 嘘をつく典型パターン。

---

## 1. 後からテストを書くと、動いていたはずの実装のバグが出る

**何が起きたか**: 既存のガード処理に対して後追いでテストスイートを書いていたところ、正規表現 `[[:space:]]-f` が**実質的に空白 2 個を要求していた**ことが判明した。そのため `git push -f` (空白 1 個) が検出をすり抜けていた。バグの発見・修正・テスト追加が 1 commit にまとまった。2026-05-18 観測。

**なぜ重要か**: 「動いている実装にテストを付け足す」作業は、単なる後始末ではなく**バグ発見の手段**である。工数を「テストを書くだけ」と見積もると、出てきたバグの修正がはみ出す。

**どう対処するか**: 既存コードへのテスト後追いには、バグが出る前提で余地を見ておく。

**出典**: 旧ハーネス `docs/tasks/list.md` task-19 (2026-05-18)。

---

## 2. 「この文字列が存在しないこと」を検査するテストは、自分で自分を止める

**何が起きたか**: ある文字列リテラルが残っていないことを検査するテストを書いた。ところが、**その文字列を消すための作業そのものが、対象の文字列に言及する必要がある**ため、テストが自分の削除作業を落とした。2026-05-14 観測。

**どう対処するか**: 段階的に抜ける。(1) 検査から一時的に除外する範囲を広げる → (2) 本体からリテラルを消して 0 件を確認する → (3) 除外範囲を元に戻す。除外の追加と撤去を別々の commit にすれば、経緯が履歴に残る。

**教訓の一般形**: 「不在」を検査するテストは、**検査対象と検査自身を区別する仕組み**を最初から持たせる。

**出典**: 旧ハーネス `docs/tasks/list.md` task-14 (2026-05-14)。

---

## 3. 失敗するテストを「想定内」で片付けると、本物のバグが隠れる

**何が起きたか**: 大きな整理作業の後、13 件のテストが失敗していた。これを 4 分類に仕分けた。

| 分類 | 対処 |
|---|---|
| 陳腐化 (対象が消えた) | 理由を書いて SKIP |
| 仕様変更 (期待値が古い) | 新しい期待値に更新 |
| 不安定 (実行ごとに変わる) | 隔離 |
| 環境依存 | 想定内の失敗として登録 |

その後のレビューで、**「想定内の失敗」に入れた 1 件が実際のバグを覆い隠していた**ことが判明した。想定内リストは 14 件から 7 件に絞られた。2026-06-02 観測。

**どう対処するか**:

- 失敗を一括で「想定内」にしない。1 件ずつ分類し、分類の理由を書く
- 「想定内の失敗」リストは最小に保つ。**判定の基準は「未説明の失敗が 0 件」**であって「失敗が 0 件」ではない
- 陳腐化したテストは削除せず、**理由を書いて SKIP か、新しい仕様に向け直す**

**出典**: 旧ハーネス `docs/tasks/list.md` task-74 (2026-06-02)。

## 4. 構造チェックは「マッチ 0 件でも通る」ことがある

**何が起きたか**: ファイル間の識別子の整合を検査するガードが、コードの書き方が変わった (`getElementById('x')` → `$('x')`) ことで**抽出対象を 1 件も拾わなくなり、無言で常に通る状態**になった。安全網が外れていることに誰も気づかなかった。2026-06-03 観測。

**どう対処するか**: 「見つけたものを検査する」形のテストには、**見つけた件数の下限**を assert する。0 件で通るテストは存在しないのと同じ。

```
抽出件数が 0 なら fail する
```

の 1 行を足すだけで防げる。

**出典**: 旧ハーネス memory `feedback_ui_rewrite_stale_smoke_regression` (2026-06-03)。

## 5. 並行性のテストは実際に並行で走らせる

複数のプロセスが同じファイルに追記する処理が、逐次テストでは通り、並列実行では 10 回中 10 回失敗した記録がある。詳細は [`subagent-operations.md`](subagent-operations.md) の項目 12 を参照。

---

## 6. 早期 return より後ろに足した処理は、無言で死ぬ

**何が起きたか**: あるスクリプトが、条件に合わないパスに対して冒頭近くで `exit 0` していた。その `exit` より後ろに**別のパスパターン向けの処理**を追記すると、その処理には決して到達しない。エラーも警告も出ないので「無音障害」になる。

**どう対処するか**: 早期 return / 早期 exit を持つ関数やスクリプトに処理を足すときは、**追加位置がガード節より前か後ろか**を必ず確認する。レビューの観点としても有効。

**出典**: 旧ハーネス `.claude/rules-details/task-management/plan-first.md` (実装者向けの警告として記載。**この警告が実際の事故に由来するかは記録から確認できない — 未確認**)。

---

## 7. 実装者の自己確認はフルスイートの代わりにならない

詳細は [`review-practice.md`](review-practice.md) の項目 9 と [`subagent-operations.md`](subagent-operations.md) の項目 7 を参照。要点: 実装者は「新しいものが動くか」しか確認しないので、旧仕様に依存したテストが壊れたことに気づけない。全面書き換えの後は、メインかレビュアーが**フルスイートを実際に走らせる**。

# 承認カード（承認・判断・人の作業を頼むときの型）

**人に何かを頼むすべての場面で使う型。** 着手の承認、設計の承認、ルールの追加、費用や動きが変わる設定、元に戻せない操作、仕様やスコープの変更、裁定（どれにするか）、人の手が要る作業。どれも、ここのカードで頼む（v2.8.0。それまでの「判断材料 5 項目」を置き換えた）。

`rules/core.md` の「**承認はカードで求める**」の本体がここ。T0 にはカードの名前と 1 行目の形だけを置き、**書き方と記入例はここ（T2）に置く**。

---

## なぜカードなのか

承認がしにくい原因は、文の長さより**順番と言葉**にある。

- **結論が最後にある。** 「何を決めてほしいか」が本文の 4 分の 3 あたりに出ると、読み終えるまで判断できない。
- **作る側の言葉で書いている。** 番号・略語・ファイルの場所は、案件を知らない人には読めない。
- **目的と効果が無い。** 「このセッションで何が起きたか」は書いても、「誰の何が良くなるか」「全体のどこか」が無い。

カードは、**読む人が判断に要るものだけを、決まった順番で、短く**出すための型。承認する人が案件を知らなくても、1 分で決められることを目指す。

## 3 つのカード

| カード | 頼むこと | 例 |
|---|---|---|
| **承認カード** | これを始めて（変えて）よいか | 機能の着手、ルールの追加、設定の変更、push や取り込み、人の権限が要る操作を AI が行うこと（`[操作]`） |
| **判断カード** | どれにするか | 方式の選択、範囲の線引き、外部との約束 |
| **人の作業カード** | 人の手で〇〇をしてほしい | 外部への申込、契約、実機での確認（`[User]`） |

迷ったら: 選択肢が 2 つ以上あるなら判断カード、AI ができず人が手を動かすなら人の作業カード、それ以外は承認カード。**箱（状態・目印）もカードに合わせる** — 判断カードは「判断待ち」、人の作業カードは目印 `[User]`、承認カードは「承認待ち」（AI が人の権限で行う操作は目印 `[操作]`）。

**推奨は AI が書く。** 案件を読み、根拠と、頼っている推測をカードに書く。雛形では機械的に埋めない。承認する人が推奨を書くことはない。

## 承認カード

### 型

```
決めること: <何を・どうするか、を 1 文>。推奨: <承認する／承認しない／条件つき（条件の文）>
目的: <誰の・何が・どう良くなるか（製品やチームのゴールとのつながり）>
位置: <計画の中の場所（何段目・何の一部か・残り）。計画の外のもの（設定・決まり）は効く範囲>
承認すると: <始まること・規模（件数・本数・期間か費用）。「戻せる」か「戻せない」>
しないと: <誰が・いつ・何に困るか。困らないなら「困らない」>
注意: <いちばん大きいリスクか、判断が要る点を 1 つ。推測は「推測」>
詳しく: <番号・リンク>／用語: docs/rules-reference/glossary.md
```

issue の本文に置くときは目印で囲み、ラベルを太字にする（GitHub で読みやすく、道具が読める）。

```
<!-- card:approval -->
**決めること**: …。**推奨**: 承認する
**目的**: …
**位置**: …
**承認すると**: …。戻せる
**しないと**: …
**注意**: …
**詳しく**: …
<!-- /card -->
```

### 各行の書き方

| 行 | 書くこと | 書かないこと |
|---|---|---|
| 決めること | 動詞で終わる 1 文。「〜を始めるか」「〜を足すか」。推奨を同じ行に。条件つきなら条件の文を括弧に | 「ご確認ください」だけ。背景の説明 |
| 目的 | 利用者・事業・チームの言葉で、良くなること | 作業の手順。「整合のため」のような作る側の理由だけ |
| 位置 | 計画の中の場所（段の名前・何の一部か・残りの件数）。計画の外なら効く範囲（このプロジェクトだけ、など） | 番号の羅列（wave 10 #630 ／ feature #651 …） |
| 承認すると | 最初に起きること、規模、**「戻せる」か「戻せない」の語**と戻し方 | 実装の細部 |
| しないと | 観測できる結果。推測は「推測」 | 脅し（「重大な問題が起きます」） |
| 注意 | 1 つだけ。推奨が何に頼っているか。承認しても今は作業が動かないなら、その理由 | リスクの羅列 |
| 詳しく | 番号とリンク。用語集の場所 | 本文の続き |

**元に戻せない操作とルールの追加は、カードの下に全文を置く。** 実行するコマンド、追記する行、変える値を、そのまま見せる（何が実行されるかを見ずに承認させない）。

## 判断カード

```
決めること: <問いを 1 文>。期限: <YYYY-MM-DD>（過ぎると <止まるもの>）
目的: <この判断で誰の何を守る・良くするか>
選択肢: A <1 行>（得る <…>・失う <…>）／ B <1 行>（得る・失う）
推奨: <A か B> — <理由を 1 行>
決めないと: <止まるもの（件数と名前）>
誰が決める: <人・会議>
詳しく: <番号・リンク>
```

- **選択肢は 3 つまで。** それ以上は「推奨の 1 つ」と「それ以外」に分ける。戻せない選択肢には「戻せない」と書く。
- **技術の判断は人に聞かない。** 置き場・番号の振り方・道具の使い方は AI が決めて報告する。人に聞くのは、目的・範囲・費用・期日・外部との約束・取り返しのつかないこと。
- **期限の無い判断は後回しにされる。** 期限を決められないなら「期限: 未定（〇〇が決まり次第）」と書く。

issue の本文では `<!-- card:decision -->` で囲む。

## 人の作業カード

```
やること: <手を動かす内容を 1 文>（所要 <分>・期限 <YYYY-MM-DD>。費用がかかるなら・費用 <額>）
誰が: <人・役割>
手順: 1. … 2. … 3. …（3 つまで。それ以上はリンク先の手順書へ）
終わったら: <どこに何を書く・貼る>
これで動くもの: <件数と名前>
```

issue の本文では `<!-- card:work -->` で囲む。

## 書き方の決まり（3 つ共通）

| 決まり | 理由 |
|---|---|
| 1 行目は結論（承認と判断は「決めること」、人の作業は「やること」） | 結論が先にあれば、残りは確かめるために読める |
| 番号・略語・ファイルの場所は「詳しく」の行だけ。本文では名前で言う | 案件を知らない人が読める |
| 値は 1 行 60 字まで、1 行目は 80 字まで、カード全体で 400 字まで | 一度に持てる量に収める。超えるなら詳しい版へ |
| 推測は「推測」、確かめていないことは「未確認」 | 推奨が何に頼っているかを見せる |
| 内部の語は初めて出るところで言い換える（段＝wave、機能のまとまり＝feature） | 用語集を開かずに読める |
| 日付は YYYY-MM-DD、量には単位（tokens・件・分・円） | 読み違えない |
| 1 回に頼むのは 1 枚。まとめて頼むなら、表で並べて最後に全体のカードを 1 枚 | 何に答えたのかが後で分かる |

**字数の数え方**: 値は、ラベルと「: 」を除いた部分の文字数（Unicode のコードポイント。Python の `len`）。1 行目の値は「。推奨: …」「。期限: …」を含めた行の残り全部。全体の 400 字は、会話の形（ラベルと「: 」を含み、改行を除く）で数える。道具（`hirai-task card`）と `tests/smoke.sh` は同じ数え方をする。

## 出し方

### 会話で頼む

カードを本文に出してから `AskUserQuestion` を出す。**選択肢は短いラベルだけ**（カードの中身を説明文に詰め込まない。切り詰められて数字が消える）。

| カード | 選択肢 |
|---|---|
| 承認カード | 承認する ／ 承認しない ／ 修正して提案し直す（推奨の選択肢に `(推奨)` を付ける） |
| 判断カード | A ／ B ／（C）／ 修正して提案し直す（推奨の選択肢に `(推奨)` を付ける） |
| 人の作業カード | 選択肢は出さない。終わったら「終わったら」の行のとおりに返してもらう |

- **承認しない**: 実行しない。**提案そのものを取り下げる**（言い換えて聞き直さない。再提案は新しい事実が出てから）。
- **修正して提案し直す**: 指摘を受けてカードを作り直し、もう一度出す。

### GitHub Project の承認ビューで受ける

GitHub Project でやることを管理しているリポでは、**着手の承認は承認ビューで受ける**。feature の本文の先頭に承認カードを置き、`hirai-task card <番号> --sync` で項目「ひとこと」「推奨」に写す。会話では「承認ビューに N 件あります」と件数を案内する。

| 答え | ボードですること | AI がすること |
|---|---|---|
| 承認する | 状態を「着手可」に動かす | 中の作業を始める |
| 条件つきで承認する | 「着手可」に動かし、条件をコメントに書く | 条件を本文の承認の記録に写してから始める |
| 承認しない | 状態を「保留」に動かし、理由をコメントに書く | 理由と再開の条件を本文に写す。言い換えて出し直さない |
| 直して出し直す | 直してほしい点をコメントに書く（状態は承認待ちのまま） | 次の会話の最初に `hirai-task comments` で拾い、カードを直して `--sync` |

- **一覧は 1 行、決めるのはカードで。** 承認ビューの「ひとこと」「推奨」は並べて選ぶためのもの。決める前に本文のカード（7 行）を開く。
- PR の取り込み（merge）は出来上がりの確認であって、着手の承認ではない。設計メモの承認を設計の PR の merge で受けることはある（着手の承認とは別）。

### 詳しい版（issue の本文）

カードのあとに、全体の中の位置（3〜5 行）→ 判断が要る点と推奨（選択肢ごとに 1 行）→ 中の作業の一覧 → リスクと戻し方 → 用語（折りたたみ）→ 機械向けの行（目印・読む資料の一覧。末尾）の順に置く。読む人は上から必要なところまで読めばよい。

### AskUserQuestion が使えないとき

ツールが無い・呼び出しが失敗した・拒否された（対話のセッションに `permissions.denyInsteadOfPrompting` を入れた環境、Channels（Telegram など）から文字だけで届いた依頼など。答える人がいる場合）ときは、カードのあとに選択肢を平文で並べた 1 通を送り、返事を待つ。**返事が来るまで次の手順に進まない。**

```
次のどれかを返信してください（番号だけで構いません）。
1. 承認する（推奨）
2. 承認しない
3. 修正して提案し直す（直してほしい点を書き添えてください）
```

判断カードなら、選択肢を `1. A …（推奨）` `2. B …` `3. 修正して提案し直す` と並べる。

- 推奨を必ず 1 つ明記する。**「はい」「OK」を承認と読むのは、推奨が「承認する」のときだけ。** 推奨が「承認しない」「条件つき」や判断カードのときは、番号で答えてもらう。それ以外の返事で迷ったら、聞き直して止まる。
- 問いが複数あるとき（`/hirai-lite:init` の手順 1 など）は問いごとに番号を振り、「全部推奨でよければ『はい』だけで構いません」と添える。
- 誰も答えない実行（`claude -p`・scheduled tasks・無人の実行に `--settings` で `denyInsteadOfPrompting` を渡したとき）では、承認の要る操作をしない。何をしたかったかを 1 行残して止まる。

## 記入例 1: 機能の着手（承認カード）

```
決めること: ログインの試行回数に上限を設けるか。推奨: 承認する
目的: 他人のパスワードを当て続ける攻撃を止め、利用者の口座を守る
位置: 公開前の「安全の仕上げ」の段。この段の残りは3件
承認すると: AIが3つの作業を順に進め、変更3本で出す。1本ずつ戻せる
しないと: 公開後、総当たりの攻撃を止める手段がない（推測。今は観測なし）
注意: 正しい利用者が5回間違えると15分待つ。問い合わせが増えるおそれ
詳しく: feature #7（作業 #31〜#33）／用語: docs/rules-reference/glossary.md
```

## 記入例 2: ルールの追加（承認カード）

```
決めること: 数を数えるコマンドの落とし穴を、決まりに1行足すか。推奨: 承認する
目的: 同じ失敗でスクリプトが止まるのを防ぎ、直す時間を減らす
位置: コードを書く作業でだけ読まれる決まり（毎回は読まれない）
承認すると: 決まりに1行足す。読む量は1,240→1,310 tokens（上限2,000）。消せば戻せる
しないと: 同じ失敗がまた起きうる（2回目。前回は直すのに30分）
注意: 3回目が必ず起きるとは言えない（推測）
詳しく: .claude/rules/code.md に追記する1行の全文は下に
```

カードの下に、追記する行の**全文**を置く（何が書かれるかを見せる）。

## 記入例 3: 費用や動きが変わる設定（承認カード）

```
決めること: 自動で手分けする設定を有効にするか。推奨: 条件つき（1週間で見直す）
目的: 複数のファイルにまたがる調べものを、手で分けずに済ませる
位置: このプロジェクトの設定だけ。ほかのプロジェクトには効かない
承認すると: 次の会話から有効。利用量（費用）が増える。設定から外せば戻せる
しないと: 手分けを毎回こちらで指示する。品質が下がるとは限らない
注意: 増える量は測れていない（未確認）
詳しく: .claude/settings.json の ultracode
```

```
目的: 問い合わせに答えられる期間と、漏れたときの害の釣り合いを取る

詳しく: #207・#350
```

## 悪い例 → 良い例

| 悪い例 | なぜ悪いか | 良い例 |
|---|---|---|
| 1 行目が「wave 10 #630 ／ feature #651 ／ task #1640」 | 番号は案件を知らない人に読めない。結論が無い | 1 行目は「決めること: 〜を始めるか。推奨: 承認する」。番号は最後の行 |
| 背景の説明から始まり、頼みごとが最後に出る | 読み終えるまで判断できない | 結論を 1 行目に。背景は「詳しく」の先へ |
| 「整合性を保つため」 | 作る側の理由で、誰の何が良くなるか分からない | 「目的: 入居者が同じ画面で迷わないように」 |
| 「予算に余裕があります」 | 数字が無く、確かめようがない | 「読む量は 1,240→1,310 tokens（上限 2,000）」 |
| 「放置すると事故が再発します」 | 推測を事実の語で書いている | 「また起きうる（2 回目）。3 回目が必ず起きるとは言えない（推測）」 |
| 戻せるかを書かない | 取り消せるかが、承認する人がまず知りたいこと | 「承認すると: …。1 本ずつ戻せる」／「…。戻せない」 |
| 「推奨: 条件つき」だけ | 何の条件か分からない | 「推奨: 条件つき（1 週間で見直す）」 |
| 置き場や番号の振り方を人に聞く | 人が決めなくてよい技術の判断 | AI が決めて、カードの「承認すると」に書く |
| カードの中身を `AskUserQuestion` の選択肢の説明に詰め込む | 切り詰められて数字が消える | カードは本文、選択肢は短いラベルだけ |
| 断られたあと、言い換えてもう一度聞く | 承認しない＝取り下げ、の約束が壊れる | 取り下げて記録に残す。再提案は新しい事実が出てから |
| 承認・判断・人の作業を 1 通に混ぜる | 何に答えればよいか分からない | カードを分ける。まとめるなら表に並べ、全体のカードを 1 枚 |

## 使う場面

`commands/` を全部 grep して洗い出した、人に頼む箇所（v2.8.0 時点）。**この表に無い場面でも、人に何かを頼むなら同じ型を使う。**

| 場面 | コマンド | どこ | カード |
|---|---|---|---|
| 既存の安全設定への差分の反映 | `init.md` | 手順 5 | 承認 |
| 承認の型の写しの置き換え | `update.md` | 手順 4 | 承認 |
| ルール追加 | `add-rule.md` | 工程 ⑥ の配置前 / 工程 ⑤ の削除候補 | 承認 |
| ルールの提案（セッション終わり） | `state.md` | 手順 11 | 承認 |
| ルールの棚卸し（降格・失効の判断） | `rules-audit.md` | 分類 3・4 を user に選ばせるところ | 判断 |
| 設計 draft の承認 | `new-draft.md` | 手順 5 | 承認 |
| タスク着手（依存が未完了のとき） | `start-task.md` | 手順 3 | 承認 |
| タスク完了（step が残っているとき）/ 既定の branch への push・PR 取り込み | `finish-task.md` | 手順 4 / 末尾 | 承認 |
| commit の分割 / 元に戻せない操作 | `commit.md` | 手順 3 / 「承認が要る操作」 | 承認 |
| 費用や動きに影響する設定変更 | `config.md` | 2（ultracode）/ 7（更新の自動化） | 承認 |
| 参照されていないファイルの削除 | `verify.md` | 6 | 承認 |
| GitHub Project の作成・項目とビューの追加 | `project-setup.md` | 2 | 承認 |
| feature の着手 | （ボードの承認ビュー） | feature の本文の先頭 | 承認 |
| 人の権限が要る操作を AI が行う | （`[操作]` の issue） | 本文の先頭 | 承認 |
| 裁定 | （判断待ちの issue） | 本文の先頭 | 判断 |
| 人が行う作業・外部の手続き | （`[User]` の issue） | 本文の先頭 | 人の作業 |

**この型を使わない場面**（頼む必要の無いところでカードを出すと、本当に要る場面での重みが落ちる）:

- 承認が要らないもの — T2 と `docs/` への追記、ルールの**削除**（`_meta.md` 条 8）、`rules-audit.md` の分類 1・2。
- 元に戻す方向の変更 — 設定を無効に戻す、費用が減る方向。
- **user が自分から指示したこと** — 「有効にして」「これを消して」と言われた操作に、改めてカードを出さない。
- 選択肢の提示であって承認ではないもの — `/hirai-lite:init` の初期設定の 3〜4 問のような「どれにしますか」。

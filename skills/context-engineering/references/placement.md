# 置き場の決め方（判断例と失敗例）

`SKILL.md` §3 の 4 択を、実際の材料にあてはめる手順。条番号はすべて `.claude/rules/_meta.md` のもの。

---

## 1. `/state save` から呼ばれたときの手順

`/hirai-lite:state save` の「次回に効くものを置く」工程は、この順で動く。**書く前に仕分ける。**

1. **拾う** — このセッションで確定した (a) 意思決定 (b) 教訓 (c) 会話で決まった取り決め を列挙する。**推測を混ぜない**。実際に決まった / 実際に詰まったものだけ。
2. **0 件なら終わる** — 「次回に効くものはありません」と 1 行返す。無理に作らない（既定は入れない）。ここで作った 1 件が、来年も毎セッション載り続ける。
3. **仕分ける** — 各件を `SKILL.md` §3 の表で 4 択に振る。
4. **自動で書く（T2 / `docs/`）** — 追記のみ。既存行の書き換え・削除はしない。
5. **承認を取る（T0 / T1 / `settings.json`）** — `AskUserQuestion` で聞く。承認されたものだけ `/hirai-lite:add-rule "<1 行>"` に渡す。**自分で `rules/*.md` に書かない**（条 7・条 8）。
6. **索引を直す** — `docs/` に新しいファイルを作ったら `CLAUDE.md` の Documents index に 1 行足す。実在しない行は消す。
7. **報告する** — 何をどこに置いたかを 1 行ずつ。承認待ちのものは「承認待ち」と明示する。

## 2. 仕分けの実例

| セッションで出たもの | 置き場 | なぜ |
|---|---|---|
| 「hook から `claude plugin update` を呼ぶ案は、動くと確かめたうえで採らなかった」 | `docs/architecture.md`（技術判断） | 意思決定の記録。規範ではないので rules に入れない。**採らなかった理由**まで書く（次に同じ案が出たとき、再調査を省ける） |
| 「`grep -c` は 0 件のとき `0` を出しつつ exit 1 を返して、`set -e` 下で落ちた」 | `docs/rules-reference/shell-pitfalls.md`（T2） | 事故 1 回目 = 記録して終わり（条 1）。bash を書く時にだけ要る知識なので、常時ロードに置く理由が無い |
| 同じ `grep -c` の事故が**2 回目** | `.claude/rules/code.md`（T1、`paths:` あり）を提案 → 承認 → `/add-rule` | 条 1 の「二度目で書く」。ただし bash を書く時だけ効くので T0 ではなく T1（条 2） |
| 「完了報告に実測値を必ず付ける」と会話で決めた | `.claude/rules/core.md`（T0）を提案 → 承認 → `/add-rule` | 全作業に例外なく効く。ただし T0 は立証が要る（条 2）ので、**承認なしには入れない**（条 8） |
| 「`git push --force` は絶対にさせたくない」 | `settings.json` の `deny` を提案 → 承認 | 元に戻せない操作。指示文では止まらない（条 5・条 9） |
| 「今日は `docs/` を `.claude/` から移した」 | どこにも書かない | git log が持っている。ファイルに二重に書くと、片方が腐る |

## 3. 層を間違えると何が起きるか

| 間違い | 起きること | 直し方 |
|---|---|---|
| 経緯や事故の詳細を T0 に書く | 毎セッション全文が載り、予算（警告 6,000 / 上限 10,000 tokens）を圧迫する。他の規範への注意も薄まる | T2 へ移し、T1 の末尾から 1 行のポインタを張る |
| T2 に「守らせたい規範」を書く | 誰も読まないので守られない。守られないルールがあると、規範全体の信用が落ちる | 規範は T0 か T1 に置く。T2 には根拠だけ残す |
| `paths:` を書き忘れて `.claude/rules/` に置く | その瞬間に T0 へ昇格し、黙って予算を食う | `tests/smoke.sh` case 5 が許可リスト外の T0 を FAIL にする。`paths:` を足すか T2 へ出す |
| T1 に「圧縮後も効いてほしい規範」を置く | `/compact` で消え、一致ファイルを読み直すまで戻らない（`official-sources.md` `[g]`） | T0 か `CLAUDE.md` に移す |
| 方法論（長い手順）を T0 に書く | 手順は毎回は要らないのに毎回載る | skill にする。本文は呼ばれた時だけ載る（`[d]`） |
| ルールを承認なしに足す | セッションのたびにルールが増え、誰も消さない。**予算が静かに尽きる** | 条 8。提案 → 承認 → 配置。削除だけは承認不要 |

## 4. T0 に上げてよいかの判定

条 2 は「T0 にするには『全作業に例外なく効く』ことの立証が要る」と書いている。立証とは次の 3 つに答えられること。

1. **例外を 1 つも挙げられないか** — 「フロントの時は違う」が 1 つでもあるなら T1。
2. **そのファイルを触らない作業でも要るか** — `docs/tasks/**` を触る時だけ要るなら T1（`paths:` に書ける）。
3. **T0 の他の 1 件と交換してでも入れるか** — 交換相手を挙げられないなら、まだ T1 でよい（条 3 の「上限は入れてよい量ではない」）。

3 つとも Yes で、はじめて T0 候補。判定は `/hirai-lite:add-rule` の工程 ③ が同じ問いを立てる。

## 5. 書いた後の検証

置いただけでは「読まれる」ことの証明にならない。`/add-rule` の工程 ⑥ が要求する実測は次の 2 つ。

- **T0** — 新しいセッションの冒頭で、その文字列がコンテキストに載っている。
- **T1** — 新しいセッションの冒頭では載らず、`paths:` の glob に一致するファイルを Read した**後**に載る。

食い違ったら frontmatter を直してやり直す。`InstructionsLoaded` hook で「どの指示ファイルが、いつ、なぜ読み込まれたか」を記録する手もある（公式が debug 用途で挙げている。`official-sources.md` `[b]` のページ）。

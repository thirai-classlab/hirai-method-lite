# コンテキストエンジニアリング

会話の中にしか無いものは `/clear` で消える。ファイルに書いても、**置き場所を間違えれば読まれないか、逆に毎セッション課金され続ける**。ここで決めるのは「**どこに置くか / どう書くか / 予算をどう守るか**」の 3 つ。

**役割分担**: 守るべき条文は `.claude/rules/_meta.md`（9 条 + 層 + 数の予算）が SSoT。このスキルは**その根拠（公式の事実）と判断手順**だけを持つ。食い違ったら条文が正。

**出典**: 本文中の `[a]`〜`[i]` は [`references/official-sources.md`](references/official-sources.md) の逐語引用と URL に対応する。推測は「未確認」と明記する（§6）。

---

## 1. 判断の骨格（4 つの問い）

1. **次のセッションで要るか** — No なら書かない。「あっても困らない」は誤り。載っているだけで毎ターン課金され、注意も薄まる `[a][f]`。
2. **いつ要るか** — 常に / 特定の作業のときだけ / 調べるときだけ → これが層を決める（§2）。
3. **止める必要があるか** — 元に戻せない操作だけ `settings.json` の `deny` / `ask`。**指示文は強制ではない** `[e]`（`_meta.md` 条 5・条 9）。
4. **誰が承認するか** — T2 と `docs/` は自動で書いてよい。**T0 / T1 / settings はユーザー承認が要る**（`_meta.md` 条 8）。承認は**判断材料つきで**求める（§3.5）。

## 2. 層 = ロードのタイミング

このハーネスの T0〜T3 は、Claude Code の**ロード規則そのもの**に対応している。層は好みではなく機構である。

| 層 | 場所 | いつ読み込まれるか | 圧縮(`/compact`)の後 | 向くもの |
|---|---|---|---|---|
| **T0** | `CLAUDE.md` / `rules/_meta.md` / `rules/core.md`（`paths:` 無し） | **毎セッションの冒頭に全文** `[b][c]` | ディスクから再注入される `[g]` | 全作業に例外なく効く規範だけ |
| **T1** | `rules/<domain>.md`（`paths:` あり） | **glob に一致するファイルを読んだ時** `[c]` | 一致ファイルを読み直すまで戻らない `[g]` | その作業のときだけ効く規範 |
| **T2** | `docs/rules-reference/**` | **明示的に Read した時だけ**（`.claude/rules/` の外なので自動発見の対象外 `[c]`） | 戻らない | 背景・経緯・事故記録・長い手順 |
| **T3** | `.claude/rules-archive/**` | 読み込まれない | — | 失効ルールの履歴 |
| skill | `skills/<名前>/SKILL.md` | **説明文は毎セッション / 本文は呼ばれた時 / `references/` は読まれた時** `[d]` | 呼んだ skill の本文は再注入（先頭 5,000 tokens まで）`[g]` | 手順・判断基準・参考資料 |

読み取れる帰結は 3 つ。

- **T0 は「毎ターン全文が載る」**。だから条文だけを置き、経緯や例外は T1/T2 へ出す。公式も CLAUDE.md は 200 行未満を目標にせよと書いている `[b]`。
- **T1 は圧縮で消える**。圧縮をまたいで効かせたい規範は T0 か `CLAUDE.md` に置く `[g]`。逆に言えば、**消えて困らないものだけを T1 に置ける**。
- **skill は先頭が生き残る** `[g]`。だから SKILL.md は結論を上に、詳細を `references/` に置く（このファイル自身がその形）。

## 3. 記録先の 4 択

`_meta.md` の条文を「セッション終わりに何が出てきたか」で引ける形に並べ直したもの。**新しい判定基準ではない**。各行の根拠となる条番号を併記する。

| 出てきたもの | 置き場 | 層 | 承認 | 根拠 |
|---|---|---|---|---|
| 事故 1 回目 / 背景・経緯 / 長い手順 | `docs/rules-reference/`（事故は `incidents.md`） | T2 | **不要**（追記のみ） | 条 1 |
| 意思決定（採った案・採らなかった案と理由） | `docs/` の該当ファイル（技術判断なら `architecture.md`） | — | **不要**（追記のみ） | 条 1 の系。規範ではないので rules に入れない |
| 事故 2 回目以降 / 特定の作業でのみ効く | `.claude/rules/<domain>.md`（`paths:` 付き） | T1 | **要** | 条 1・条 2・条 8 |
| 事故 2 回目以降 / 全作業に効く（要立証） | `.claude/rules/core.md` | T0 | **要** | 条 2・条 3・条 8 |
| 元に戻せない操作 | `settings.json` の `deny` / `ask` | — | **要** | 条 5 |

- **自動で書いてよいのは T2 と `docs/`**。追記だけで、既存行の書き換え・削除はしない。理由: 読み込まれない領域なので、間違って書いても他のセッションの挙動を変えない。
- **ルール（T0 / T1 / settings）は自分で書かない**。ユーザー承認を取り、承認されたものだけ `/hirai-lite:add-rule` の 6 工程（分類 → 重複検査 → 層決定 → 記述最適化 → 予算 → 配置とロード検証）に渡す。手順を二重に持たない（条 7・条 8）。
- **迷ったら T2**。降格は後からできるが、T0 に入れたものは誰も外さない。

判断に迷う具体例と、層を間違えた時に起きることは [`references/placement.md`](references/placement.md) にある。

### 3.5 承認は判断材料つきで求める

T0 / T1 / `settings.json` への追加を提案するときは、**何をしたいか / なぜ / しないとどうなる / トレードオフ / どうやるか** の 5 点を本文に示してから `AskUserQuestion`（承認する / 承認しない / 修正して提案し直す）を出す（`rules/core.md`「承認は判断材料つきで求める」）。**「どうやるか」には層と、予算の現在値 → 追加後の値を数字で書く。**

この型は**ルール追加に限らずすべての承認に効く汎用規範**なので、本体はこの skill ではなく T2 に置いてある → **`docs/rules-reference/approval-template.md`**（書き方・記入例 3 つ・悪い例と良い例・使う場面の一覧）。**承認不要なもの（T2 と `docs/` への追記、ルールの削除）にこの型は使わない。**

## 4. どう書くか

書式・禁止語彙・肯定形は `_meta.md` の「記述テンプレート」が SSoT。ここには**なぜそう書くのか**だけを置く。

- **判定できる条件にする** — 公式も「Use 2-space indentation」のように**検証できる具体性**を勧めている `[b]`。`適切に` `必要に応じて` は判定不能なので `_meta.md` が禁止語彙にしている。
- **理由を 1 つ添える** — 「なぜそう振る舞ってほしいか」を書くと、モデルは説明から一般化する `[h]`。ただし T0 では 1 行に収める（例 1 つ・失効条件 1 つ）。
- **矛盾を残さない** — 2 つの指示が食い違うと、モデルはどちらかを任意に選ぶ `[b]`。だから `/add-rule` の工程 ② が重複・矛盾検査を必ず通る。
- **`@import` を使わない** — 公式に「imports は起動時に展開されて context に入る」「分割は整理には役立つが context は減らない」とある `[b]`。`_meta.md` の同条の根拠がこれ。
- **強制の語を安売りしない** — 公式は「CLAUDE.md は context であって強制設定ではない。必ず止めたいなら PreToolUse hook を使え」と明記している `[e]`。止まらないものを「BLOCK する」と書くと、存在しない制約に萎縮する（`_meta.md` 条 9）。

## 5. 予算をどう守るか

- **T0 は合計で警告 6,000 / 上限 10,000 tokens**（`_meta.md` 条 3、`tests/smoke.sh` case 4 が計測）。上限は「入れてよい量」ではなく、既定は T1（条 2）。
- **数も予算**（`_meta.md`「数の予算」、case 6 が計測）— hook 5 / command 12 / skill 3 / smoke case 10。skill は本文こそ遅延ロードだが、**説明文は毎セッション載る** `[d][f]` ので数で抑える。
- **測ってから足す**。実測コマンドは `/hirai-lite:add-rule` の工程 ⑤ にある（置き場の解決を含む）。目分量で「空きがある」と判断しない。
- **超えたら降格**。T0 → T1 → T2 の順に落とす。削除は承認不要（条 8）。

上位の原則は Anthropic の記事にある **「推論中に最適なトークン集合を選び、保つための戦略」** `[a]`。トークンが増えるほど正確に取り出す力が落ちる（context rot）ため、注意は有限資源として扱う。このハーネスの T0 予算・数の予算・T2 の物理分離は、いずれもその実装である。

## 6. 確認できなかったこと（推測で埋めない）

- **T0 の 6,000 / 10,000 tokens、T1 の 1 file 2,000 tokens に対応する公式の数値は無い**。公式が示すのは「CLAUDE.md は 200 行未満を目標」`[b]` と「SKILL.md は 500 行未満」`[d]` だけ。本ハーネスの数値は自前の設計値である。
- **`docs/` 配下が「絶対に自動ロードされない」と明言した公式文は見ていない**。確認できたのは「`.claude/rules/` 配下の `.md` が再帰的に発見される」`[c]` までで、T2 の安全性はその**外側に置く**ことから導いた推論である。
- **`/clear` と「閉じて開き直す」が全点で同一だとは公式に書かれていない**（`commands/state.md` に同じ但し書きがある）。
